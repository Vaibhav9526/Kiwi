# KIWI — Deep App Walkthrough Script

**Purpose:** a scene-by-scene script for explaining *the application itself* —
what to open, in what order, what to point at, and what to say. Written to the
as-built app (routes: `mail · compose · setup · settings · security · search ·
contacts · filters · disposable`), not slideware.

**Total runtime:** ~10–12 min full depth. `[QUICK]` marks the compressible bits.

---

## How to proceed — the demo order at a glance

| # | Screen / route | What it proves |
|---|---|---|
| 0 | Terminal: `docker compose up` + `npm run tauri dev` | Real stack, real servers, not a mockup |
| 1 | Setup wizard (`#/setup`) | Account onboarding + **first TLS evidence** |
| 2 | Mailbox (`#/mail/all-inboxes`) | It's a *real mail client* first |
| 3 | Message reader → security pill → finding dialog | Evidence per message |
| 4 | Composer (`#/compose`) | Policy enforcement at send time |
| 5 | Security Center (`#/security`) | Findings, events, audit chain, exports |
| 6 | Re-scan / diff | Remediation is *provable* |
| 7 | Settings → Security + certificate viewer | Per-account posture, cert chain |
| 8 | Device pairing + lock + authenticator | Trust has teeth |
| 9 | Disposable (`#/disposable`) + Integrations | Consent boundary in action |
| 10 | Themes (Settings → Appearance) | Same evidence, any theme — honesty |
| 11 | Admin UI (`localhost:3001`) + mobile scaffold | The org plane |
| 12 | Close | Map features → PS deliverables |

## SCENE 0 — Before you show the app (30s)

**Show:** terminal.

```bash
docker compose up -d mailpit greenmail   # real SMTP :1025, POP3 :1100, IMAP :1143
cd kiwi-app && npm run tauri dev         # the desktop client
```

**Say:**
> "Before the UI — the setup is part of the story. Those are *real* mail
> servers running locally: Mailpit for SMTP and POP3, GreenMail for IMAP.
> KIWI talks actual SMTP, IMAP, and POP3 over the wire to them — there are no
> mock transports anywhere in the product. Everything you're about to see is
> generated by real protocol traffic on this machine."

**Why it matters:** establishes credibility — demo skeptics assume slides.
You've just shown a Rust/Tauri binary driving real wire traffic.

## SCENE 1 — Account setup wizard (`#/setup`) (~60s)

**Do:** walk the add-account flow (Mailpit/GreenMail test account).

**Say:**
> "Setup looks like any mail client — address, password, go. But watch what
> happens at verification: when KIWI probes the account, the transport layer
> captures a `TlsObservation` — the TLS version negotiated, the cipher suite,
> the key exchange, whether there's forward secrecy, the certificate chain,
> and the STARTTLS behavior. That's the first piece of *evidence*, captured
> at the protocol layer — not inferred, not a checkbox the server claimed.
> The account card shows the result right here, including the certificate."

**Point at:** the inline TLS observation + cert summary in the verify step.

**Why it matters:** this is the *endpoint vantage* — your SIH26159
differentiator — appearing in a boring, familiar flow.

## SCENE 2 — The mailbox (`#/mail/all-inboxes`) (~90s)

**Show:** the four-pane shell — folder tree, message list, reader, agenda
rail. Click through folders, multi-select a couple of messages, show the
unified inbox across accounts.

**Say:**
> "This is the point that's easy to miss: KIWI is a *complete* mail client.
> Folder tree with smart counts, a unified 'All Inboxes' across accounts,
> tabbed message list, thread-card reader, an agenda rail on the right.
> Quick filters, multi-select, drag-to-folder, context menus, reply prefill,
> snooze, templates, keyboard shortcuts. Three themes — light is default,
> there's dark and a high-contrast accessibility theme.
>
> The reason we built a real client under the security layer: a security
> tool people won't *use* protects nobody. KIWI has to win as a mail client
> before its security matters."

**Point at:** the honesty badge if running in demo mode — *"and if the
backend is unreachable, the UI says the data is demo — it never fakes a live
state."*

[QUICK: skip drag-to-folder / templates if short on time]

## SCENE 3 — Message reader → security pill → finding detail (~90s)

**Do:** open a message. Click the security pill in the reader header → the
finding-detail dialog opens.

**Say:**
> "Every message carries a security pill — `secure`, `warning`, `danger`, or
> `unknown` — driven by the session that delivered it. Grey means *we don't
> know*, and it's deliberately grey — never painted green.
>
> Click it and you get the finding with its **evidence attached**: the rule
> that fired, severity, confidence, the typed evidence — frame numbers,
> stream offsets, a redacted excerpt — plus impact and remediation steps.
> The evidence renders verbatim with a copy button; the UI is not allowed to
> summarize or hide it.
>
> If AI enrichment is enabled, it renders here too — inside a labeled
> 'AI-generated, not authoritative' collapsible, and it must cite the finding
> keys it grounds in. The verdict is the rule engine's; the AI only
> *explains* it."

**Why it matters:** this one dialog is the whole design philosophy —
verdict + evidence + remediation + optional AI explanation, in one place.

## SCENE 4 — Composer + send path (`#/compose`) (~60s)

**Do:** open composer; if an org policy is loaded, address a message to a
blocked external domain → the policy banner appears; show send options
(undo-send grace window, send-later scheduling).

**Say:**
> "Compose is normal — until policy says otherwise. When the organization
> plane restricts recipient domains or requires minimum transport security,
> the evaluation happens *before* send: allow, warn, or block — with the rule
> ID and scope note shown in the banner. Send itself goes through a real
> queue with an undo-send grace window and scheduled send-later — none of it
> is cosmetic.
>
> And under the hood, the outbound SMTP connection gets the same
> `TlsObservation` treatment — sending is assessed exactly like receiving."

[QUICK: if no org policy is loaded, just show undo-send and move on]

## SCENE 5 — Security Center (`#/security`) (~2 min — the centerpiece)

**Do:** navigate to Security view. Walk the three areas: findings list →
security events table → audit log.

**Say:**
> "This is the posture-assessment surface — the heart of the problem
> statement.
>
> **Findings**, worst-first: every rule that fired, its severity, the session
> it belongs to, and the evidence behind it. Severity is the shared
> vocabulary everywhere — secure, warning, danger, unknown, locked.
>
> **Security events**: a chronological table — timestamp, account, category,
> severity, summary — every evaluated session and trust event, each clickable
> to its detail.
>
> **The audit chain**: every mutation the app makes lands in a hash-chained
> log — each record carries the hash of the previous one, verified from the
> genesis record every time it opens. If I corrupt this file on disk and
> reload — *[do it if you can]* — the app doesn't hide it: this banner says
> `audit-corrupt`, and 'Re-check' runs a real re-verification. Tampering is
> *surfaced*, not repaired silently and not panicked over.
>
> **Exports**: forensic report and security events as JSON — canonical bytes
> wrapped in a self-verifying SHA-256 envelope. Anyone can prove the report
> wasn't altered after the fact. That export is the artifact a SOC forwards
> upstream."

**Why it matters:** findings + events + tamper-evident audit + verifiable
export = "comprehensive forensic reports" from the PS deliverables, live.

## SCENE 6 — Re-scan / diff (~45s)

**Do:** from the account security panel or security center, run a re-scan
and show the diff view.

**Say:**
> "Assessment without a re-check is a snapshot; KIWI closes the loop.
> Findings have stable keys — rule ID plus the session subject — so scanning
> before and after a fix produces a real diff: what's **new**, what's
> **resolved**, what's **unchanged**, and where severity moved. 'We fixed
> the expired certificate' becomes a resolved row you can *show* — proof of
> remediation, not a claim of it."

---

## SCENE 7 — Settings → per-account security + certificate viewer (~60s)

**Do:** Settings → KIWI Security section → account card → open the
certificate viewer.

**Say:**
> "Each account gets a security card: the sessions seen, finding counts, the
> last scan time, the trust state. The certificate viewer shows the chain the
> endpoint actually saw — subject, issuer, serial, validity window, SHA-256
> fingerprint, signature algorithm — per hop. Again: captured, not inferred —
> this is what the server presented to *this* client, which matters because
> TLS 1.3 hides it from anyone on the wire."

---

## SCENE 8 — Device trust, pairing, lock (~90s)

**Do:** Settings → Security → Devices → "Add device" (pairing dialog shows a
QR payload). Explain lock: if you can trigger a lock, show the overlay +
authenticator dialog states (waiting → approved/denied/expired).

**Say:**
> "KIWI's trust model extends beyond the mail protocol. A companion
> authenticator — a React Native app — pairs over QR with asymmetric
> challenge-response; the device key never leaves the phone's keystore, and
> challenges are bound to the device, the session, and the event with replay
> protection.
>
> Endpoint signals feed a trust engine. When trust drops far enough — say, a
> suspicious remote-session indicator — the app **locks**. And the lock is
> real: it's enforced in the Rust IPC layer across the *entire* command
> surface, so a compromised renderer can't talk its way past it — unlocking
> requires approval on the paired device. Content panes go inert; this isn't
> a modal you can click behind."

**Honesty footnote to say if asked:** "the authenticator is a working
scaffold — production hardening is gated on contract rulings — and it's
fail-closed: it errs toward denying, never toward approving."

---

## SCENE 11 — The org plane: admin UI + mobile (~60s)

**Do:** open `localhost:3001` (kiwi-admin + kiwi-admin-ui).

**Say:**
> "For organizations there's a separate control plane — a Node service on
> PostgreSQL with its own localhost admin UI: organizations, domains, users,
> roles, recipient-domain policies, and mail-flow *metadata* — sender,
> recipient, timestamp, security status — **never message bodies**. Policy
> authored here is what produced the composer banner earlier. The mobile
> authenticator scaffold is the same story on the phone — QR pairing,
> keystore-bound keys, approve/deny."

## SCENE 12 — Close: map it back to the problem statement (~45s)

**Say:**
> "So, mapping back to SIH26159's deliverables: protocol identification —
> SMTP, IMAP, POP3, native. STARTTLS detection and downgrade indicators —
> with positive evidence, not inference. TCP stream and TLS handshake
> reconstruction — in the forensics engine, both live at the endpoint and
> passive from PCAP. Certificate extraction and analysis — per hop, at the
> endpoint. Weak crypto and deprecated versions — a 37-rule deterministic
> catalog. Forward-secrecy assessment — from the key-exchange mechanism.
> AI risk scoring and prioritization — grounded in cited findings, never
> authoritative. Exportable forensic reports — JSON now, HTML/PDF as views
> over the same aggregate, self-verifying. And the dashboard — everything
> you just saw.
>
> KIWI doesn't ask you to trust it. It shows you the evidence."

## Appendix A — If they ask "what's under the hood"

> "A Rust 2024 workspace — ten crates: `kiwi-mail` is the protocol engine
> (real SMTP/IMAP/POP3, MIME, SQLite + FTS5 store, rules, transport capture),
> `kiwi-forensics` is the assessment engine (PCAP ingest, reassembly, the
> rule catalog, scoring, report exports), `kiwi-core` holds the trust and
> session model, `kiwi-pair` owns device pairing, `kiwi-mailauth` does
> SPF/DKIM/DMARC over fail-closed DNS, `kiwi-sandbox` runs risky opens in a
> disposable WSL2 guest, plus autoconfig, contacts, integrations, and the
> Tauri shell. `unsafe` is forbidden workspace-wide; credentials live only
> in the OS credential store; and the React renderer is *untrusted by
> design* — every IPC command validates, lock-gates, and audits."

## Appendix B — Demo failure playbook

| If it breaks | Recovery line / move |
|---|---|
| Backend down | App badges itself **demo mode** — lean in: "watch, it tells you instead of faking" |
| No Docker | Renderer alone: `npm run dev` + same demo-mode honesty story |
| Can't trigger a lock | Narrate the lock semantics + show the lock-gated IPC code path |
| No PCAP handy | Use the account security panel — live `TlsObservation` findings are the same engine |

## Appendix C — The three sentences to never break

1. "**Deterministic rules decide; AI only explains.**" (never "AI detects")
2. "**Unknown renders grey — never a fake green.**" (fail closed over fabricate)
3. "**Captured, not inferred.**" (evidence is protocol-layer fact)
